# NarrateFlow 视频配音独立技术方案

版本：V3 独立评审修正版  
日期：2026-06-08  
依据：基于《NarrateFlow 视频配音方案 V2》重新评审与收敛，不依赖任何既有项目代码积累。

## 1. 项目定位

NarrateFlow 是一个面向“无声视频 + 已准备好的旁白文稿”的自动配音与视频重定时系统。

系统输入：

- 无声视频文件，例如 `.mp4`。
- 已写好的旁白文稿，例如 `.txt` 或结构化脚本 JSON。
- 可选：参考音色、发音词典、人工锁定的时间点。

系统输出：

- 带旁白音轨的成片视频。
- 可复查的中间产物，包括视频理解结果、TTS 音频、时间轴对齐文件和人工修正记录。

明确不做：

- 不做口型对齐。
- 不做画面重绘。
- 不把视频理解模型输出当作物理真值。
- 不追求第一版全自动闭眼出片。

核心设计原则：

- 真实时间轴优先：视频边界、帧率、时长必须来自 `ffprobe`、OpenCV、PySceneDetect 等确定性工具。
- 大模型只给候选：VLM 输出视觉摘要、动作候选、情绪标签，但不直接决定最终时间轴。
- 人工审核内置：关键节点允许人类快速修正，而不是事后救火。
- 分阶段演进：先做稳定 MVP，再逐步加入本地 VLM、高级对齐、数据飞轮和微调。

## 2. 总体架构

```text
输入
  ├── video.mp4
  └── narration.txt
        │
        ▼
Stage 0: 资产探测与标准化
  ├── ffprobe 获取视频真实时长、fps、分辨率
  ├── 文稿解析、分句、段落编号
  └── 生成 project_manifest.json
        │
        ▼
Stage 1: 视频结构化理解
  ├── PySceneDetect 检测镜头边界
  ├── OpenCV 抽取关键帧 / 短片段帧序列
  ├── VLM 生成视觉摘要、动作候选、OCR/实体/意境标签
  └── 输出 video_meta.json
        │
        ▼
人工关卡一：视觉理解审核
        │
        ▼
Stage 2: 旁白音频生成
  ├── 文本清洗与发音词典替换
  ├── TTS 分段生成音频
  ├── 检测每段音频真实时长
  ├── 可选 forced alignment 获取词级时间戳
  └── 输出 narration_audio_manifest.json
        │
        ▼
人工关卡二：配音听审
        │
        ▼
Stage 3: 时间轴对齐与视频重定时
  ├── 段落与镜头窗口综合匹配
  ├── 滑窗合并镜头
  ├── 轻微变速 / B-roll 补画面 / 短定格
  └── 输出 timeline_plan.json
        │
        ▼
Stage 4: FFmpeg 渲染合成
  ├── 视频重定时
  ├── 音频混音
  ├── 编码导出
  └── 输出 final_video.mp4
```

## 3. 对 V2 方案的修正结论

### 3.1 Qwen3-VL 时间戳只能作为候选

V2 中将 Qwen3-VL 的 Text-Timestamp 能力描述为“直接吐出动作精确秒数”。这个方向可以探索，但不能作为工程真值。

修正方案：

- `start_time`、`end_time` 必须来自视频物理时间轴。
- VLM 输出的动作时间只记录为 `time_hint`。
- `time_hint` 需要绑定置信度和来源。
- Stage 3 对齐时可以参考动作候选，但不得无校验地使用。

### 3.2 显存安全需要硬指标

V2 中“12G 显存永远绰绰有余”的判断过于乐观。多帧视觉输入的真实消耗不仅来自模型权重，还来自视觉 token、上下文、KV cache、输出 token 和运行时碎片。

修正方案：

- 每个镜头最多抽取 `8-12` 帧。
- 单帧长边默认限制到 `600px`。
- 每次 VLM 输出 token 设置硬上限。
- 记录每次推理耗时、显存峰值和失败原因。
- 3060 上 VLM 与 TTS 默认不同时常驻。
- 若显存超阈值，按顺序降级：降帧数、降分辨率、短片段切分、切换更小模型、切换云端 provider。

### 3.3 定格不是主对齐策略

V2 中“动作帧定格”是有价值的兜底方案，但如果作为主要策略，会造成明显卡顿。

修正方案：

对齐策略优先级调整为：

1. 合并相邻镜头。
2. 使用语义相近的中性 B-roll。
3. 对视频做轻微变速，建议 `0.90x-1.10x`。
4. 在低运动帧或动作结束点短定格，单次建议不超过 `0.8s`。
5. 超出阈值时标记为 `needs_review`，由人工压缩文稿或调整窗口。

### 3.4 意境标签只能作为软特征

V2 强调“艺术意境”可以解决字面语义代沟，这一点有启发，但不能成为主要匹配依据。

修正方案：

时间轴匹配应综合以下特征：

- 视频物理顺序。
- 音频时长与镜头时长。
- 视觉摘要语义相似度。
- 物理标签。
- OCR 文本。
- 主体动作。
- 意境标签。
- 人工锁定点。

其中时间顺序、时长和物理标签优先级高于意境标签。

### 3.5 Thinking 输出需要结构化解析

V2 中建议用正则提取最后一个 JSON 块。这个方法可以作为兜底，但不能作为主要解析方案。

修正方案：

- Prompt 明确要求只输出 JSON。
- 尽量使用模型或框架提供的结构化输出能力。
- 引入 schema 校验。
- 对关键字段做类型转换和范围校验。
- 解析失败只重跑当前窗口，不污染整条流水线。
- 正则提取最后 JSON 只作为最后兜底。

### 3.6 微调飞轮延后

V2 中“500 条修正数据即可微调质变”的表述需要收敛。

修正方案：

- 第一阶段把人工修正数据作为评测集。
- 第二阶段作为 few-shot 示例池。
- 第三阶段沉淀规则库和发音词典。
- 只有当数据规模、标注一致性和质量评估体系成熟后，再考虑 LoRA 或 TTS 微调。

## 4. 核心中间数据结构

### 4.1 `project_manifest.json`

```json
{
  "schema_version": "3.0",
  "video_path": "input/video.mp4",
  "script_path": "input/narration.txt",
  "video": {
    "duration_sec": 128.4,
    "fps": 30.0,
    "width": 1920,
    "height": 1080
  },
  "created_at": "2026-06-08T20:00:00+08:00"
}
```

### 4.2 `video_meta.json`

```json
{
  "schema_version": "3.0",
  "windows": [
    {
      "window_id": "w0001",
      "start_time": 0.0,
      "end_time": 5.2,
      "boundary_source": "scenedetect",
      "visual_summary": "一名程序员在夜晚的办公室中看着屏幕思考",
      "physical_tags": ["person", "office", "computer", "night"],
      "art_tags": ["focused", "pressure"],
      "visible_text": [],
      "actions": [
        {
          "label": "person touches head",
          "time_hint": 3.4,
          "confidence": 0.58,
          "source": "vlm_candidate"
        }
      ],
      "source_frames": [
        {
          "time": 2.6,
          "path": "frames/w0001_mid.jpg"
        }
      ],
      "review_status": "pending"
    }
  ]
}
```

字段约束：

- `start_time` / `end_time` 是真实窗口边界。
- `time_hint` 是候选动作点，不是最终对齐点。
- `review_status` 支持 `pending`、`approved`、`fixed`、`rejected`。

### 4.3 `narration_audio_manifest.json`

```json
{
  "schema_version": "3.0",
  "segments": [
    {
      "paragraph_index": 1,
      "text": "今天，我们来看一个本地视频配音系统。",
      "audio_path": "audio/p001.wav",
      "duration_sec": 4.12,
      "word_timestamps": [],
      "tts_provider": "voxcpm2",
      "review_status": "approved"
    }
  ]
}
```

字段约束：

- `duration_sec` 必须读取实际音频文件得出。
- `word_timestamps` 可选，但字段预留。
- 读错词应通过发音词典修正后单段重跑。

### 4.4 `timeline_plan.json`

```json
{
  "schema_version": "3.0",
  "segments": [
    {
      "paragraph_index": 1,
      "audio_start": 0.0,
      "audio_end": 4.12,
      "matched_window_ids": ["w0001"],
      "video_start": 0.0,
      "video_end": 5.2,
      "match_score": 0.84,
      "retime_strategy": "slight_speed",
      "review_status": "approved"
    }
  ]
}
```

## 5. 模型选型建议

### 5.1 视频理解模型

推荐路线：

- MVP：云端 VLM 或较稳定本地 VLM 作为 baseline。
- P1：接入 Qwen3-VL-8B-Thinking 作为本地实验 provider。
- P2：根据压测结果决定是否保留 8B，或引入更小模型 fallback。

Qwen3-VL-8B-Thinking 的定位：

- 适合生成视觉摘要、动作候选、氛围标签。
- 适合做多帧理解和镜头语义描述。
- 不适合单独承担最终物理时间轴决策。

本地部署要求：

- 支持 Ollama / GGUF / 其他本地推理框架均可。
- 必须支持推理超时、局部重试、显存峰值记录。
- 必须有模型不可用时的 fallback。

### 5.2 TTS 模型

VoxCPM2 可以作为 V3 的重点 TTS 候选，但需要先压测。

验证项：

- 中文旁白自然度。
- 48kHz 输出稳定性。
- 长文本分段一致性。
- 数字、英文、专业名词、多音字。
- Windows CUDA 兼容性。
- Mac MPS / MLX 可用性。
- 单段重跑速度。

MVP 阶段建议：

- 不把 TTS 模型写死。
- 设计 `tts_provider` 接口。
- 先保证“分段生成 + 实际时长检测 + 单段重跑 + 发音词典”跑通。

## 6. Stage 1：视频结构化理解

### 6.1 物理切片

使用 PySceneDetect 或等价工具检测镜头边界。

输出：

- 镜头开始时间。
- 镜头结束时间。
- 镜头时长。
- 切片置信度或切片来源。

注意：

- 硬切镜头适合有明显转场的视频。
- 对长镜头需要二级切分。
- 对录屏、PPT、软件演示类视频，应加入 OCR 或界面变化检测。

### 6.2 抽帧策略

短镜头：

- 小于 `5s`：抽中间帧或首中尾三帧。

长镜头：

- 大于 `5s`：最多抽 `8-12` 帧。
- 必要时按局部动作变化或帧差抽帧。
- 不建议无上限按每秒 2 帧堆给 VLM。

### 6.3 VLM 输出要求

Prompt 应要求模型输出：

- 一句话视觉摘要。
- 物理标签。
- 可见文字。
- 主体动作候选。
- 意境标签。
- 不确定性说明。

同时明确：

- 不要编造不可见信息。
- 动作时间是估计值。
- 输出必须符合 JSON schema。

## 7. Stage 2：旁白音频生成

### 7.1 文本分段

文本分段的目标不是单纯按标点切句，而是让每段 TTS 具备稳定语气与可控时长。

建议：

- 每段控制在约 `25-60` 个中文字。
- 遇到标题、术语、数字、英文缩写时先做规范化。
- 保留原文和 TTS 友好文本两个字段。

### 7.2 发音词典

需要内置发音纠错机制：

- 多音字。
- 品牌名。
- 专业术语。
- 英文缩写。
- 数字和单位。

示例：

```json
{
  "CUDA": "库达",
  "Qwen": "千问",
  "3060": "三零六零"
}
```

### 7.3 音频真实时长

每段 TTS 生成后，必须读取音频文件真实时长。

禁止：

- 用文字字数估算时长后直接进入视频对齐。

允许：

- 用字数估算做初步排期。
- 最终对齐以音频真实 duration 为准。

## 8. Stage 3：时间轴对齐

### 8.1 综合匹配评分

每个旁白段落与候选视频窗口组合计算分数：

```text
score =
  0.25 * order_score
+ 0.25 * duration_score
+ 0.20 * visual_semantic_score
+ 0.10 * physical_tag_score
+ 0.10 * ocr_score
+ 0.05 * action_score
+ 0.05 * art_tag_score
```

权重可配置，但原则是：

- 时间顺序和时长优先。
- 物理语义优先于主观意境。
- 人工锁定点拥有最高优先级。

### 8.2 滑窗组合

旁白段落可能长于单个镜头，因此应允许一个段落匹配多个连续窗口。

约束：

- 默认保持视频原始顺序。
- 不允许无解释地跨越大量无关镜头。
- 对低分匹配标记 `needs_review`。

### 8.3 重定时策略

按优先级执行：

1. 原速使用。
2. 合并相邻镜头。
3. 轻微变速。
4. B-roll 补画面。
5. 短定格。
6. 人工 review。

定格选择点：

- 优先低运动帧。
- 优先动作完成后。
- 优先句子停顿点附近。
- 不默认使用最后一帧。

## 9. Stage 4：FFmpeg 合成

### 9.1 渲染职责

FFmpeg 负责：

- 视频切片。
- 局部变速。
- 短定格。
- 音频拼接。
- 混音。
- 编码输出。

### 9.2 硬件加速

Windows / NVIDIA：

- 可尝试 `h264_nvenc`。

macOS：

- 可尝试 `h264_videotoolbox`。

兜底：

- 硬件编码失败时切换软件编码 `libx264`。

### 9.3 输出检查

导出后应自动检查：

- 成片是否存在。
- 成片时长是否接近目标音频时长。
- 是否有静音段异常。
- 是否有黑帧或冻结过长段。
- FFmpeg 是否返回错误。

## 10. Human-in-the-loop

### 10.1 视觉审核

审核内容：

- 镜头切片是否合理。
- 视觉摘要是否准确。
- OCR 是否漏掉关键信息。
- 动作候选是否明显错误。
- 意境标签是否跑偏。

操作：

- 修改 `video_meta.human.json`。
- 不覆盖 `video_meta.ai.json`。

### 10.2 配音审核

审核内容：

- 发音。
- 断句。
- 语速。
- 情绪。
- 段落之间是否割裂。

操作：

- 单段重跑 TTS。
- 更新发音词典。
- 标记段落 `approved`。

### 10.3 时间轴审核

审核内容：

- 旁白与画面是否语义匹配。
- 是否出现明显卡顿。
- 是否定格过长。
- 是否需要手动锁定起止点。

操作：

- 修改 `timeline_plan.human.json`。
- 从 Stage 4 重新渲染。

## 11. 显存与进程管理

### 11.1 运行策略

RTX 3060 12GB：

- 默认串行运行 VLM 与 TTS。
- VLM 阶段结束后释放模型。
- 轮询显存水位后再启动 TTS。

Mac M4 Pro 24GB：

- 可尝试模型常驻。
- 但必须保留 `release_after_stage` 配置。
- 不默认认为统一内存一定安全。

### 11.2 监控指标

每次任务记录：

- VLM 推理耗时。
- VLM 显存峰值。
- TTS 推理耗时。
- TTS 显存峰值。
- FFmpeg 渲染耗时。
- JSON 解析失败次数。
- 人工修改次数。

这些指标用于决定是否需要降级模型或调整抽帧策略。

## 12. 数据飞轮

数据飞轮的优先级应从低风险到高风险推进。

### 12.1 评测集

保存：

- 原视频。
- 抽帧。
- AI 输出。
- 人工修正。
- 最终时间轴。
- 最终视频。
- 质量评分。

用途：

- 比较不同 VLM。
- 比较不同 Prompt。
- 比较不同 TTS。
- 回归测试。

### 12.2 Few-shot 池

当人工修正稳定后，将典型案例作为 few-shot 示例。

用途：

- 约束 JSON 格式。
- 纠正常见意境误判。
- 提升同类视频输出稳定性。

### 12.3 规则库

规则库包括：

- 发音词典。
- OCR 替换规则。
- 物理标签到文案语义的映射。
- 常见镜头类型的对齐偏好。

### 12.4 微调

微调是后期路线，不是 MVP 路线。

启动条件：

- 有稳定 schema。
- 有足够人工修正样本。
- 有独立评测集。
- 能量化微调前后的收益。

## 13. 技术路线图

### P0：MVP 跑通

目标：

- 输入视频和旁白。
- 生成 TTS 音频。
- 基于物理镜头窗口完成基本对齐。
- FFmpeg 输出成片。

任务：

- `project_manifest.json`
- `video_meta.json`
- `narration_audio_manifest.json`
- `timeline_plan.json`
- 基础人工审核流程。

验收：

- 3-5 分钟视频可完整跑通。
- 支持从任意阶段重跑。
- 人工可修改视觉理解和时间轴。

### P1：本地 VLM 接入

目标：

- 接入 Qwen3-VL-8B-Thinking 或同类本地 VLM。

任务：

- 抽帧预算控制。
- 结构化输出。
- schema 校验。
- 局部失败重试。
- 显存峰值记录。

验收：

- 3060 上不 OOM 或可自动降级。
- 本地 VLM 输出可进入 Stage 3。
- 与云端 baseline 可对比。

### P2：对齐质量提升

目标：

- 减少卡顿和错配。

任务：

- 综合评分匹配。
- 滑窗镜头组合。
- 轻微变速。
- B-roll 补画面。
- 短定格。
- forced alignment 可选接入。

验收：

- 长句不再默认尾帧长定格。
- 每个匹配结果有可解释分数。
- 低置信段落自动进入人工 review。

### P3：TTS 质量提升

目标：

- 提升旁白自然度和发音稳定性。

任务：

- VoxCPM2 压测。
- 发音词典。
- 单段重跑。
- 长文本分段优化。
- 音频上下文承接。

验收：

- 读错词可稳定修正。
- 单段重跑不影响其他阶段。
- 输出音频时长稳定可检测。

### P4：产品化与数据飞轮

目标：

- 降低人工审核成本。
- 形成可持续优化闭环。

任务：

- 审核 UI。
- 评测集。
- few-shot 池。
- 规则库。
- 可选微调实验。

验收：

- 同类视频人工修改次数下降。
- Prompt 或模型切换后可回归测试。
- 数据资产可用于后续训练或评估。

## 14. 主要风险与兜底

| 风险 | 影响 | 兜底 |
| --- | --- | --- |
| VLM 动作时间不准 | 定格点错位 | 只作为候选，低置信进入人工审核 |
| 本地模型显存溢出 | 任务失败或机器卡顿 | 降帧、降分辨率、换小模型、云端 fallback |
| TTS 读错词 | 成片不可用 | 发音词典、单段重跑 |
| 文稿过长 | 视频对齐困难 | 文稿压缩建议、镜头合并、B-roll、人工 review |
| 长定格观感差 | 画面像卡住 | 限制定格时长，优先变速和补画面 |
| JSON 解析失败 | 下游无法执行 | schema 校验、局部重试、人工修正 |
| 微调收益不确定 | 投入大、收益不明 | 先做评测集和 few-shot，不提前投入微调 |

## 15. 最终方案判断

基于 V2 方案的方向，NarrateFlow 技术路线整体可行，但必须将“大模型自动精确对齐”的设想改为“确定性工具提供真实时间轴，大模型提供语义候选，算法与人工审核共同完成最终决策”。

最稳妥的落地方式是：

1. 先用物理时间轴和 TTS 真实时长跑通 MVP。
2. 再把 Qwen3-VL 作为增强型视频理解 provider 接入。
3. 然后升级时间轴匹配和重定时策略。
4. 最后再考虑数据飞轮、few-shot 和微调。

这样做的好处是：即使模型输出不稳定，系统仍然可运行、可解释、可人工修正、可逐步提升。
